# 🎮 GameKey Store — магазин цифровых товаров с автовыдачей ключей

Веб-приложение для продажи игровых ключей и пополнений (Steam, Epic Games, Xbox, PlayStation, Razer Gold, Google Play и др.): витрина с каталогом, создание заказа, приём платежа, **моментальная автоматическая выдача ключа** и админ-панель для управления заказами и пулом ключей.

Ключевая особенность — надёжность при конкурентной нагрузке: обработка оплаты идемпотентна, а один ключ никогда не выдаётся дважды, даже если приходит много параллельных вебхуков.

**Стек:** NestJS 10 + TypeScript + TypeORM (PostgreSQL) · Nuxt 3 (Vue 3 + Pinia + TailwindCSS) · Docker Compose

---

## 📦 Возможности

- **Витрина товаров** — каталог с пополнениями и подарочными картами, баннеры, адаптивная вёрстка.
- **Создание заказа и «оплата»** — эмуляция платёжного вебхука (готовая точка для подключения реального платёжного шлюза).
- **Автовыдача ключа** сразу после оплаты — резервируется ровно один свободный ключ из пула товара.
- **Промокоды** — процентная скидка с жёстким лимитом использований (не превышается даже под параллельными запросами).
- **Страница статуса заказа** — по номеру заказа покупатель видит статус и выданный ключ.
- **Админ-панель** (`/admin`) — статистика, список заказов, пул ключей, добавление ключей, ручная выдача ключа.
- **Защита от гонок и идемпотентность** на уровне транзакций БД (подробнее ниже).

## ⚙️ Как это работает

### Жизненный цикл заказа

```
┌──────────┐   POST /api/orders   ┌─────────┐   вебхук оплаты   ┌─────────┐
│ Витрина  │ ───────────────────▶ │ created │ ────────────────▶ │   paid  │
└──────────┘                      └─────────┘                   └────┬────┘
                                                                     │ автовыдача ключа
                                                       ┌─────────────▼──────────────┐
                                                       │        delivering          │
                                                       └──┬──────────┬──────────┬───┘
                                          ключ найден      │          │          │  ключей нет /
                                          и выдан          │          │          │ поставщик не ответил
                                                  ┌────────▼───┐ ┌────▼─────┐ ┌──▼────────────┐
                                                  │ delivered  │ │out_of_   │ │ delivery_     │
                                                  │  (ключ в   │ │  stock   │ │  failed       │
                                                  │  ответе)   │ └──────────┘ └───────────────┘
                                                  └────────────┘    (восстановимо —        │
                                                                    можно выдать ключ      │
                                                                    вручную из админки)   │
```

- `created` — заказ создан, оплата не получена.
- `paid` — платёж подтверждён вебхуком.
- `delivering` — идёт резервирование ключа и обращение к поставщику.
- `delivered` — ключ выдан; значение подмешивается в ответ как `assignedKeyValue`.
- `out_of_stock` — в пуле товара не осталось свободных ключей (восстановимо).
- `delivery_failed` — все поставщики вернули ошибку (восстановимо).
- `failed` — платёжный вебхук пришёл со статусом `failed`.

### Гарантии: идемпотентность и отсутствие двойной выдачи

1. **Транзакции + блокировки строк.** Обработка вебхука и выдача ключа выполняются в одной транзакции. Заказ и строка ключа берутся с `SELECT … FOR UPDATE` (`setLock('pessimistic_write')`).
2. **Уникальные события.** У каждого вебхука свой `event_id` (уникальный индекс в `webhook_event`). Повторный вебхук с уже обработанным `event_id` не вызывает повторную выдачу — заказ возвращается в текущем состоянии.
3. **Деferred-вебхуки.** Если вебхук пришёл раньше, чем создан заказ, событие сохраняется как `pending` и обрабатывается при следующем (ретрайном) запросе платёжного шлюза.
4. **Ровно один ключ.** Ключ из пула резервируется не массовым `UPDATE`, а выборкой одной свободной строки под блокировкой. Параллельные заказы после ожидания перечитывают условие `isUsed = false` и берут следующую свободную строку — ключ не выдаётся дважды и не теряется.
5. **Промокоды.** Списание использования промокода и создание заказа происходят в одной транзакции с блокировкой строки промокода — лимит `maxUses` не превышается даже под параллельными запросами.

### Мок поставщика

`backend/src/orders/orders.service.ts` содержит упрощённую логику доставки через двух поставщиков (`supplier_primary`, `supplier_fallback`) со случайным отказом (~15%). Каждая попытка логируется в `delivery_log` с уникальным `request_id`. Для продакшена этот метод заменяется реальными HTTP-вызовами поставщиков (с той же семантикой идемпотентности по `request_id`).

### Таблицы БД

`product`, `key_pool`, `order`, `promo_code`, `webhook_event`, `delivery_log`. Схема создаётся автоматически (`synchronize: true` — только для разработки).

## 🚀 Быстрый старт (Docker)

### Требования

- Docker + Docker Compose (≥ v2)
- Node.js ≥ 20 (нужен только для сборки статики фронтенда)
- npm

### Шаги

Фронтенд собирается в статику **на хосте**, а nginx-образ только раздаёт её и проксирует API. Поэтому сначала соберите `.output`, затем поднимите сервисы:

```bash
# 1. Установить зависимости и собрать статику фронтенда
cd frontend
npm install
npm run build
cd ..

# 2. Собрать и запустить все сервисы (db, backend, frontend)
docker compose up -d --build

# 3. Проверить, что всё поднялось
docker compose ps
```

После этого:

| Сервис | Адрес |
|---|---|
| Магазин (frontend) | http://localhost |
| Backend API (напрямую) | http://localhost:3000 |
| Админ-панель | http://localhost/admin |

### Демо-данные (первый запуск)

При первом запуске БД пустая (создаются только таблицы). Наполните её демо-данными — товарами, промокодами и пулом ключей:

```bash
docker compose exec backend node dist/seed.js
```

Скрипт создаст 8 товаров, 4 промокода и от 20 до 70 случайных ключей на каждый товар. **Запускать только на пустой БД** — повторный запуск добавит дубликаты.

### Частые операции

```bash
# Пересобрать и перезапустить только фронтенд после правок UI
cd frontend && npm run build && cd .. && docker compose up -d --build frontend

# Посмотреть логи бэкенда
docker compose logs -f backend

# Остановить
docker compose down
```

## 🔧 Переменные окружения

Бэкенд читает конфигурацию из переменных окружения (пример — `backend/.env.example`). В Docker они заданы прямо в `docker-compose.yml`.

| Переменная | По умолчанию (docker) | Описание |
|---|---|---|
| `DATABASE_HOST` | `db` | Хост PostgreSQL (для локального запуска — `localhost`) |
| `DATABASE_PORT` | `5432` | Порт PostgreSQL |
| `DATABASE_USERNAME` | `store_user` | Пользователь БД |
| `DATABASE_PASSWORD` | `store_pass_123` | Пароль БД |
| `DATABASE_NAME` | `digitalstore` | Имя БД |
| `PORT` | `3000` | Порт HTTP-сервера API |
| `ADMIN_TOKEN` | `admin_secret_token_2024` | Токен доступа к админ-панели (**обязательно смените для продакшена**) |

Фронтенду переменные не нужны: он обращается к API по относительным путям (`/api`, `/admin-api`), которые проксирует nginx.

## 🔌 API

Все публичные точки — под префиксом `/api`, админские — `/admin-api` (требуют заголовок `x-admin-token`).

### Публичный API

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/products` | Список товаров каталога |
| `GET` | `/api/products/:id` | Товар по id |
| `GET` | `/api/products/:id/key-pool` | Сколько свободных ключей у товара |
| `POST` | `/api/orders` | Создать заказ. Body: `{ productId, userEmail?, userIp?, promoCode? }` |
| `GET` | `/api/orders/:orderNumber` | Статус заказа (после выдачи содержит `assignedKeyValue`) |
| `POST` | `/api/orders/:orderNumber/pay` | Эмуляция оплаты и автовыдачи ключа (удобно для тестов) |
| `GET` | `/api/promo-codes/:code` | Информация о промокоде |
| `POST` | `/api/promo-codes/validate` | Проверка промокода. Body: `{ code, productId? }` |
| `POST` | `/api/promo-codes/apply` | Атомарное списание одного использования промокода |
| `POST` | `/api/webhooks/payment` | Вебхук платёжного шлюза (см. ниже) |

**Вебхук оплаты:**

```json
POST /api/webhooks/payment
{
  "event_id": "evt_unique_id",
  "order_id": 123,
  "status": "paid"           // или "failed"
}
```

Ответ: `200 { "received": true }`. Повторная отправка того же `event_id` — идемпотентна (ключ не выдаётся дважды). Вебхук со статусом `failed` переводит заказ из `created`/`paid` в `failed`.

### Админ-API (заголовок `x-admin-token: <ADMIN_TOKEN>`)

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/admin-api/stats` | Статистика: всего / выполнено / в обработке / ошибки |
| `GET` | `/admin-api/orders?status=&limit=&offset=` | Заказы (пагинация, фильтр по статусу) |
| `GET` | `/admin-api/orders/:orderId` | Заказ + история доставок (`delivery_log`) + ключ |
| `POST` | `/admin-api/orders/:orderId/deliver` | Ручная выдача ключа. Body (опц.): `{ key_value }` |
| `GET` | `/admin-api/key-pool` | Пул ключей по товарам (всего / использовано / доступно) |
| `POST` | `/admin-api/key-pool` | Добавить ключи товару. Body: `{ productId, keys: [...] }` |

Ручная выдача идемпотентна: для уже выданного (`delivered`) заказа вернёт тот же ключ. Позволяет «доиграть» заказы в статусах `out_of_stock`, `delivery_failed`, `created`, `paid`, `delivering`.

### Демо-сценарий (curl)

```bash
TOKEN=admin_secret_token_2024

# 1. Список товаров
curl http://localhost/api/products

# 2. Создать заказ на товар #3 (Steam Gift Card $20)
curl -s -X POST http://localhost/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"productId":3,"userEmail":"guest@test.com","userIp":"127.0.0.1"}'

# 3. «Оплатить» и получить ключ (эмуляция вебхука)
curl -s -X POST http://localhost/api/orders/ORD-XXXXXXXXXXXX/pay

# 4. Проверить статус и выданный ключ
curl -s http://localhost/api/orders/ORD-XXXXXXXXXXXX

# 5. Статистика админки
curl http://localhost/admin-api/stats -H "x-admin-token: $TOKEN"

# 6. Ручная выдача ключа заказу 123
curl -s -X POST http://localhost/admin-api/orders/123/deliver -H "x-admin-token: $TOKEN"
```

## 🛠 Админ-панель

Откройте **http://localhost/admin** и введите токен (по умолчанию `admin_secret_token_2024`). Панель автоматически обновляет данные каждые 10 секунд.

- **orders** — таблица заказов; у заказов в статусах `out_of_stock` / `delivery_failed` доступна кнопка «Выдать ключ».
- **keys** — пул ключей по товарам.
- **add-keys** — загрузка новых ключей для товара (по одному на строку).

Токен хранится в `localStorage` браузера. Для продакшена смените `ADMIN_TOKEN` и используйте HTTPS.

## 🧑‍💻 Локальная разработка (без Docker)

### Вариант 1 — сервисы в Docker, правки кода на хосте

Удобный цикл: поднять `db` и `backend` в Docker, а фронтенд пересобирать по мере правок (см. «Частые операции» выше). Это проверенный путь и не требует дополнительных настроек прокси.

### Вариант 2 — всё локально

1. **База данных** — свой PostgreSQL либо через Docker:
   ```bash
   docker compose up -d db
   ```

2. **Backend** (порт `3000`):
   ```bash
   cd backend
   npm install
   cp .env.example .env          # поправьте DATABASE_HOST=localhost, если БД не в Docker-сети
   npm run start:dev
   ```
   API будет доступен на http://localhost:3000.

3. **Frontend** (SPA без SSR):
   ```bash
   cd frontend
   npm install
   npm run dev
   ```
   Nuxt-dev сервер поднимется на http://localhost:3000 — **порт занят бэкендом**, поэтому задайте другой, например `PORT=3001 npm run dev`.

   Обратите внимание: в dev-режиме браузер ходит в API по относительным путям `/api`, `/admin-api`, поэтому для работы магазина настройте в `nuxt.config.ts` dev-прокси этих префиксов на адрес бэкенда (либо используйте готовую docker-сборку из Варианта 1 — там прокси уже настроен в nginx).

> **Замечание.** Поскольку `nuxt.config.ts` отключает SSR (`ssr: false`), финальный артефакт — статика в `frontend/.output/public`, которую и раздаёт nginx в Docker.

## ✅ Проверка надёжности

- **Конкурентный смоук:** `backend/smoke/concurrency_smoke.py` гоняет десятки параллельных вебхуков по одному заказу и убеждается, что ключ выдан ровно один раз, а лимит промокода не превышен.
- Идемпотентность, атомарное резервирование ключа и защита лимитов промокода реализованы на уровне транзакций TypeORM (см. раздел «Гарантии»).

## 📝 Примечания

- `synchronize: true` в TypeORM создаёт схему автоматически — это удобно для разработки, но **не подходит для продакшена** (используйте миграции).
- «Платежи» в проекте эмулируются. Для реальных платежей подключите платёжный шлюз к `POST /api/webhooks/payment`.
- Мок поставщика в `orders.service.ts` замените на реальную интеграцию (контракт: идемпотентность по `request_id`, ключ возвращается один раз).
